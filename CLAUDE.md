# CLAUDE.md

Contexte pour reprendre le projet dans Claude Code.

## Projet

DevCardBattle (DCB) : jeu de cartes stratégique DevOps, inspiré de AWS Card Clash. Objectif final : duels multijoueurs tour par tour sur un site web. Jalon actuel : collection de cartes (galerie, éditeur). Développé en local, publié en démo sur dcb.mathod.fr.

Design source : fichier Figma `DevCardBattle` (fileKey `pG6o4Zvee9YjNf3AzGKV81`), composant `card` (node `30:1386`), calques `cardTypeStroke/*` (`30:1488`), `skin/*` (`30:1652`). Finitions : section `foilLayer` (`107:1435`, composants `foilLayer/Basic|Gold|Stars|Glitter|Shards|Rainbow`, statiques ; l'ancien `rarityLayer` y a été fusionné). La section `Collection` (`36:1521`) contient les cartes maquettées ; le frame `Board` (`36:2621`) esquisse le plateau de jeu.

## Stack

- Rust workspace, edition 2024
- `dcb-core` : types de domaine + validation, sans dépendance serveur
- `dcb-server` : axum 0.8, askama 0.16, sqlx 0.9 (SQLite), toml, htmx 2 embarqué
- Source de vérité : `cards/<slug>.toml` + `cards/art/` (commités par l'utilisateur). SQLite (`data/cache.db`) n'est qu'un cache reconstruit au démarrage et via `POST /reload`
- Page `/regles` : texte dans `rules/regles.toml` (lu au démarrage et au rechargement, en cas d'erreur la dernière version valide reste affichée), mise en forme `***terme***` et montants `$…` via `rules::inline`. Exemples de cartes tirés au hasard par `db::random_card` (cartes remplies d'abord)
- Documentation en pages (`views::DocPage`, un seul gabarit `rules.html` découpé par `self.is("…")`, navigation de gauche, sommaire de droite construit par `rules.js` depuis les `[data-toc]` de la page) : `/regles` Overview (pitch, chiffres, début de partie, victoire), `/regles/basics` (5 types, anatomie, finitions, glossaire), `/regles/core-concepts` (cycle de jeu, cycle de vie d'une app, économie, incidents, interactions, plateau), `/regles/getting-started` (première partie, deck, créer une carte, skins, contours, autres réglages), `/regles/releases`, `/regles/roadmap`. Sections de texte dans `regles.toml` (`[glossary]`, `[economy]`, `[board]`…, `draft = true` affiche la pastille Brouillon). Patch notes dans `rules/releases.toml`, roadmap dans `rules/roadmap.toml` (statuts study, planned, doing, done ; une entrée faite cite sa version), lus avec les règles
- Releases et roadmap : à chaque mise en ligne, ajouter une version en tête de `rules/releases.toml` (Nouveau, Changé, Corrigé) et mettre à jour `rules/roadmap.toml`
- Bandes de skins, finitions et contours (Basics et Getting Started) : une bande qui défile en boucle par réglage (skins classiques, skins animées, finitions, contours ; contenu doublé, copie `aria-hidden`), avec compteur ; chaque exemple est une carte différente tirée au hasard (cartes remplies d'abord, pioche relancée si la collection est plus petite). Skins décrites dans `[[concepts.skin.classic|animated]]` et contours dans `[[concepts.shape.items]]` de `regles.toml` (clé → `concepts::skin_style`, CSS `sk-*`/`dyn-*` de `concepts.css`). Vue zoomée au clic (`concepts.js`, `#card-modal` avec `data-frames`/`data-click`) : description de la skin, et choix de la catégorie qui tire une carte du type parmi les `<template class="tpl-card">` de toute la collection (cartes remplies d'abord)
- `/regles/concepts` : document « Carte DCB v2 » (pistes de design restantes : idées ; les skins et les contours sont passés sur `/regles`. Décision : la page reste telle quelle, les idées sont de la conception et ne vont pas dans la doc), rendu par l'app comme `/regles`. Texte dans `rules/concepts.toml` (rechargé avec les règles ; chaque section a une `key` qui choisit le rendu, clé inconnue signalée), cartes tirées au hasard à chaque affichage, module `concepts.rs`, gabarit `concept_card.html`, `static/concepts.css` et `concepts.js` (sommaire, fenêtre agrandie, ASCII calculé dans le navigateur sur un canvas)
- Ordre d'écriture : fichier TOML (atomique : tmp + rename) puis cache, sous le verrou de `CardStore`
- Comptes : seconde base SQLite persistante `data/app.db` (`migrations-app/`, module `auth`), jamais reconstruite. Argon2id, sessions en cookie `dcb_session` (SHA-256 du jeton en base). Rôles `Role` : `user` (Joueur), `creator` (Créateur), `admin` ; migration `0002_creator_role.sql` (table reconstruite, sessions gardées). Pages publiques (accueil, galerie, fiches, règles, concepts, API en lecture, illustrations) via `MaybeUser` et `AppState::ctx_for`. `CurrentUser` (sinon redirection `/login?next=`), `AdminUser` (403), `EditorUser` (admin ou créateur, éditeur ouvert : `DCB_EDITOR` ou `DCB_SANDBOX` ; joueur 403, éditeur coupé 404). Plus de page de connexion : `GET /login` rend l'accueil avec le panneau `.login-pop` de la barre du haut ouvert (`Ctx.login`), un échec aussi (401) ; `app.js` remplit `next` avec la page courante ; déconnexion vers `/`. Middleware `same_origin_only` contre le CSRF. Pas d'inscription : comptes créés par l'admin (`/admin/users` ou `dcb-server user add`)
- Prod : image `ghcr.io/mathod95/dcb` (Dockerfile, workflow `image.yml`), `DCB_EDITOR=0`, `DCB_SANDBOX=1`, volume `/data`. Hébergée sur le serveur Saltbox de l'utilisateur (Traefik), à dcb.mathod.fr. Les vraies cartes se créent en local, puis push et nouvelle image. Préprod : branche `preview` → image `ghcr.io/mathod95/dcb:preview` (workflow `image.yml`), conteneur `dcb-preview` relancé tout seul par Watchtower (`--label-enable`, polling 60 s) ; `DCB_CHANNEL=preview` sur ce conteneur affiche la pastille canal · version (première entrée de releases.toml) · commit (`DCB_COMMIT`, build arg) en bas à droite de l'accueil. Dockerfile avec cargo-chef (dépendances en cache entre deux builds)
- Mode démo (`DCB_SANDBOX=1`) : les créateurs créent des cartes (`Ctx.can_create`), mais ne modifient ou ne suppriment que les leurs (`AppState::may_modify`, 403 sinon) ; l'admin modifie tout ; `/reload` reste admin. L'auteur de chaque carte est gardé en mémoire (`AppState.owners`, « Mes cartes » = `/gallery?mine=1`) et les cartes sont écrites dans `cards/` du conteneur : tout disparaît au redéploiement. Bandeau `demo_banner.html`, pas de « Fichiers à commiter »
- Galerie : panneau de filtres à gauche (formulaire GET, une case par valeur, envoyé à chaque changement). `db::Filter` : OU dans un réglage, ET entre réglages, clés répétables dans l'URL ; valeur inconnue ignorée par la galerie, 400 sur l'API. `db::list` lit tout et filtre en Rust. Compteurs croisés : cartes qui passent les autres réglages avec cette valeur
- Galerie, panneau Affichage à droite : paramètres `v_skin`, `v_foil`, `v_shape`, `v_size`, `v_badge`, `v_title`, `v_desc`, `v_effect`, `v_refs`, `v_relief`, `v_bg`, `v_version` (`web::GalleryView`, `VIEW_KEYS`) appliqués à l'affichage de toutes les cartes, jamais enregistrés ; `v_skin` accepte aussi les skins de la documentation (`concepts::skin_style`, conteneur `.st sk…`, concepts.css et concepts.js chargés seulement dans ce cas). Menus ouverts et position de défilement gardés entre deux rechargements (`sessionStorage` `dcb-gallery-ui`, `hx-swap="innerHTML show:none"`), panneaux sans barre de défilement visible. Les cartes s'agrandissent pour remplir la largeur (`--grid-scale` calculé par le script de `gallery.html`, base 0,61). Les radios appartiennent au formulaire des filtres (`form="gal-form"`), les valeurs vides sont retirées de l'adresse ; les liens des filtres gardent l'affichage. Pas de choix du nom de fichier du bloc Code : `effect.yaml` par défaut
- Requêtes SQL en `&'static str` (sqlx 0.9 refuse les chaînes construites à l'exécution) : composer avec `concat!` et la macro `columns!` dans `db.rs`

## Conventions

- Textes de l'interface en français ; termes techniques en anglais (deploy, cluster, pod, scaling...)
- Pas de tiret cadratin dans les textes
- Méthode : plus de maquettes en artifact. On code directement dans l'app, on pousse sur la branche `preview`, l'utilisateur valide sur la préprod (dcb-preview.mathod.fr), puis on passe en prod avec `gh workflow run promote.yml` (main avance jusqu'à preview, l'image `preview` devient `latest`, sans rebuild). Toujours demander l'accord avant de passer en prod. Captures de cartes en taille normale (374×574) en attendant l'image
- Cible : navigateur sur ordinateur uniquement. Pas de vue mobile à concevoir ni à tester
- Navigation : la barre du haut ne contient que le logo (retour au menu) et, à droite, « Se connecter » (visiteur) ou le menu du compte avec le rôle (Mes cartes, Comptes, Mon compte, Se déconnecter selon les droits). Le menu d'accueil propose Galerie, Documentation (/regles), Nouvelle carte (créateur, admin) et Comptes (admin). Création aussi depuis « + Nouvelle carte » de la galerie
- La rareté n'existe plus en tant que champ : c'est la finition `foil` (basic, gold, stars, glitter, shards, rainbow) qui en tient lieu. L'ancien champ TOML `rarity` est lu pour compatibilité (`Foil::from_legacy`), jamais écrit
- Contour : champ `shape` (`Shape` dans dcb-core), `solid` par défaut et non écrit dans le TOML. CSS via `.card[data-shape=…]` dans `card.css`. `sweep` ne tourne qu'au survol dans la galerie, en continu sur la fiche et dans l'aperçu
- Taille : champ `size` (`Size` dans dcb-core), `normal` par défaut et non écrit dans le TOML. `normal` : deux cases de coût de 163 px ; `compact` : chips de 40 px avec icône et bloc Effect de 135 px au lieu de 110. CSS via `.card[data-size=…]` (le `data-size` de `.card-name` est la taille de police du nom, sans rapport). Plus de case Rarity sur les cartes : la finition se voit à son reflet et sur la fiche
- Badge de type : champ `badge` (`Badge` dans dcb-core), `text` par défaut et non écrit dans le TOML. `text` : le type à droite du bloc du nom (Figma) ; `image` : pastille `.card-badge` de la couleur du type, avec son icône, en haut à gauche de l'illustration, et le nom prend toute la largeur. CSS via `.card[data-badge=…]`. Le schéma de l'anatomie force `text` et la taille normale
- Nom : champ `title` (`Title` dans dcb-core), `block` par défaut et non écrit dans le TOML. `image` : plus de bloc nom, l'illustration monte à 19 px et fait 250 px de haut, le nom est écrit en bas sur un dégradé (`.card-art-shade`), et le type s'affiche en badge quel que soit `badge` (`CardView.badge` vaut alors `image`, le fichier garde la valeur choisie). CSS via `.card[data-title=…]`. Le schéma de l'anatomie force `block`
- Description : champ `desc_style` (`DescStyle` dans dcb-core), `classic` par défaut et non écrit dans le TOML. `untitled` : bloc sans le titre Description, le texte commence en haut ; `comment` : plus de bloc Description, le bloc Effect monte à 279 px (180 px de haut, 205 en compact) et la description en est la première ligne (`.card-comment`, `# …` en italique). CSS via `.card[data-desc=…]`, filtre `desc` dans la galerie. Le schéma de l'anatomie force `classic`
- Cartes citées : champ `refs` (`Refs`), `plain` par défaut et non écrit. `linked` : dans l'effet, le nom d'une autre carte de la collection (5 lettres au moins, mot entier, insensible à la casse) prend la couleur de son type (`.card-ref`). `CardView::cite(&RefIndex, link)` remplit `effect_html` : lien vers la carte sur la fiche, simple `<span>` dans la galerie, l'aperçu et l'éditeur ; les autres pages (règles, anatomie) gardent le texte simple
- Background : champ `background` (`Background`), `plain` par défaut et non écrit ; `tinted` : le fond prend la couleur du type (`.card[data-bg=tinted] .card-skin`, mélangé aux couleurs de la skin et du relief), indépendant du contour. Le contour `thin` (Filet, 1 px) remplace l'ancien `tinted` (qui teintait aussi le fond) ; aucune carte ne l'utilisait. Filtre `bg`, affichage `v_bg`
- Relief : champ `relief` (`Relief`), `flat` par défaut et non écrit. `soft` : ombre douce sous chaque bloc et case de coût (`--relief-shadow`, plus marquée sur Dark et les skins de la documentation), avec toutes les skins ; avec Light seule (hors `.sk`), en plus fond un peu plus soutenu et bordures plus légères sur les blocs neutres seulement (jamais sur l'illustration, teintée par le type, ni sur les cases de coût, qui gardent leur couleur). CSS via `.card[data-relief=…]`
- Version : champ `version` (`CardVersion`), `v1` par défaut et non écrit (migration `0013_version.sql`). `v2` : `CardDraft::effective()` impose shape topbar, size compact, badge image, title image, desc_style comment, relief soft, background tinted, effect_style code, refs linked (skin, foil, effect_file libres) ; les réglages de la carte restent dans le fichier pour revenir en v1. `CardView::new` et `db::field` (filtres) utilisent la carte effective ; `data-version` sur la carte. Galerie : `v_version` s'applique d'abord, les autres `v_*` passent par-dessus. Éditeur : en v2 les champs fixés (`data-v2-locked`) sont grisés en CSS (`:has`). Filtre `version`
- Bloc Effect : champ `effect_style` (`EffectStyle`), `text` par défaut et non écrit ; `code` : bloc `.card-code` façon éditeur (repris de Carte DCB v2), en-tête avec `effect_file` (texte libre, 32 caractères, vide : `effect.yaml`, non écrit s'il est vide), une ligne YAML par effet via `concepts::effect_rows` (`CardView.effect_rows`), description en commentaire `# …` si `desc_style` = comment, cartes citées en `.y-ref` si `refs` = linked. Filtre `effect` dans la galerie. Police JetBrains Mono chargée dans `base.html`
- Les enums (type, skin, foil, shape, size, badge, title, desc_style, refs, relief, background, version, effect_style) sont stockés en texte via leur `slug()` ; ajouter une valeur = variante dans `dcb-core` + style CSS, sans migration
- Bloc illustration : contour teinté par la couleur du type (25 %). Carte sans illustration : bloc `.card-art.is-empty` teinté par la couleur du type, motif de points et icône du type (dans `card.html`, une icône par type)
- Les cotes de `card.css` viennent du Figma : ne pas les changer sans vérifier la maquette
- Pas de cartes de démo ni de seed : le dépôt ne contient que les cartes créées par l'utilisateur
- Le slug (nom du fichier) ne change pas quand une carte est renommée
- L'illustration n'est jamais prise depuis le client lors d'une mise à jour (`current_art` sert uniquement à l'aperçu) ; les uploads sont identifiés par leurs octets, pas par leur extension

## État

Fait : carte v2 (`version`, plusieurs réglages d'un coup), background teinté combinable avec les contours, panneau Affichage de la galerie, bloc Effect façon code avec nom de fichier libre (`effect_style`, `effect_file`), documentation en six pages avec Releases et Roadmap, cartes citées dans l'effet (`refs`) et relief de la skin claire (`relief`), description classique, sans titre ou en commentaire (`desc_style`), nom sur l'illustration (`title`), filtres multiples de la galerie dans un panneau latéral, badge de type dans le nom ou sur l'illustration (`badge`), skins classiques et animées sur la page des règles (bandes défilantes, vue zoomée par catégorie), taille normale ou compacte (`size`) et retrait de la case Rarity, mode démo de l'éditeur en prod (`DCB_SANDBOX`), hébergement sur Saltbox, contours sélectionnables (`shape`), jeu ouvert aux visiteurs avec connexion dans la barre du haut, rôles Joueur, Créateur et Admin, administration des comptes, image Docker sur GHCR, page des règles (/regles), finitions (`foil`, qui remplace la rareté, reflet suivant la souris), 86 cartes de l'utilisateur dans `cards/`, CRUD complet avec upload, cartes en TOML versionnées, rechargement des fichiers, aperçu htmx en direct, API JSON, tests HTTP de bout en bout, CI.
